## 环境与职责

## 文件与接口

- tools/pipeline/cli.mjs：doctor、run --issue N、status --issue N、export-logs --issue N。
- config.mjs：loadLocalConfig(path)，严格校验本机路径、workerId、Profile、超时、maxFixRetries=2，配置不含密钥。
- github.mjs：通过可配置 argv 数组的外部 gh 凭据代理执行 gh api。读取 Issue，原子创建领取 ref，状态记录，幂等查询/创建 PR。禁止任意合并 API。不要执行任意 Issue 命令文本。
- workspaces.mjs：acquireTaskWorkspace(task)，独立分支/工作区和排他锁。可用独立 clone 代替共享 gitdir 的 worktree，防止 Windows workspace-write 沙箱阻止 Git 元数据写入。规范化真实路径，拒绝 main/master、非独立根目录和脏工作目录。
- dsh.mjs：runDsh(task,workspace,attempt)，stdin UTF-8，stdout JSONL、stderr、进程退出码、超时、session ID。调用本机配置的 electron executable + cli entry + --profile ... --json -。从可信的外部 credentialCommand 的 stdout 在内存中取得模型 API 密钥，注入精确命名 env；不输出、不写日志；所有日志去除秘密；使用 shell:false、windowsHide:true。
- review.mjs：review(task,headSha)，独立只读审查工作区、固定命令验证、Codex exec 的 JSONL、output-schema。审查先核验 base/head，不能把 exit 0 当通过。允许本机配置只读 Codex Profile；明确调用 Superpowers requesting-code-review、verification-before-completion。
- runner.mjs：runTask(issueNumber)，状态机、持久 attempt/fixRetries，首次实现+最多两轮修复；通过 awaiting-merge，不关闭 Issue、不合并；失败和环境问题 blocked。
- logs.mjs：本机完整记录与去敏导出；Issue/PR 只共享摘要和去敏记录链接；不会上传原始认证资料。
- schemas/task.schema.json、schemas/review.schema.json：严格字段及类型。
- templates/implement.md、templates/review.md：固定提示，不用 Issue 文本拼 shell。
- pipeline.test.mjs：Node 内置测试。外部进程/远端调用可注入适配器，测试实际状态机行为，不写空壳或检查源字符串的假测试。
- .pipeline/config.example.json、docs/agents/pipeline.md、.github/ISSUE_TEMPLATE/agent-task.yml：非敏感配置、双机步骤与操作入口。

## 任务清单

Issue body 含一个 JSON fenced block，严格 schema 字段：schemaVersion=1, repository, issueNumber, title, approvedBy, baseRef, baseSha, branch, allowedPaths, acceptance(string[]), verificationCommands({command,args[]}[]), maxFixRetries=2。
本机配置 approvedUsers=['xyz537']。只有 Issue 作者和清单 approvedBy 属于白名单、包含 ready-for-agent、清单 issueNumber/仓库匹配、baseSha 存在于 baseRef、分支为 agent/issue-<N>-<slug>、字段白名单及类型均符合时才领取。记录 canonical JSON 的 sha256；每轮执行和发布前复查，不用后来编辑的未批准需求继续执行。测试命令只能使用本机预置允许的命令名和参数模式，首轮允许 node --check game.js、node --check test.cjs、node test.cjs。

## 互斥、恢复与 Git

本机并发1，OS独占锁以实际路径为键；可通过常驻锁持有进程或可靠本地锁实现。用 GitHub 原子创建 refs/heads/automation/claim/issue-N 领取，指向含 workerId/runId/specDigest/baseSha 的领取提交。两台机器竞争只有一个创建成功。重复轮询不得让新 worker 通过同名标签抢任务。

领取记录、状态和 fixRetries 远端持久化；重启或第二台机器不得重置。网络写超时先查询已存在 ref/PR/状态；不盲重建。领取失联 fail closed，不能 TTL 自动抢占；人工确认旧进程停止才允许转移。发布前验证 owner、记录版本和预期远端 head。

发布只允许该任务精确的 agent/issue-N-slug，基础 setup/codex-dsh-pipeline 和 automation/claim 或日志专用 refs；拒绝 main/master、force、通配 refspec 和删除。无 merge API、无 auto-merge。PR 用 baseRef 与业务分支幂等查建，初建 Draft；Issue 保持打开。

每个 DSH 开发工作区和 Codex 审查工作区独立，不能同时使用同一工作树。不要使用用户游戏主工作目录。远程冲突和任务摘要/HEAD 变化停止，旧审查不能通过。

## 成功与失败判定

DSH 必须 completed final、exit0、自测通过且实际允许范围内有业务改动；空改动不能成功。控制器可以在 DSH 退出后对已核验 diff 执行 git commit；若 DSH 已提交则核验其提交。全部 GitHub 推送由发布代理负责。

独立验证命令必须重新运行，输出、exitCode、开始/结束时间与精确 headSha 关联。Codex verdict schema 要求 headSha、verdict(pass/needs-fix/blocked)、acceptanceResults、findings、testEvidence；只有所有验收通过、独立测试通过且无 Critical/Important 才 pass。

初轮 attempt0；needs-fix 可启动 attempt1、attempt2，共三轮。每轮保存具体反馈和失败测试；用已知同 cwd 的 session ID 续跑或提供完整修复提示开新 Session。基础设施失败（认证、沙箱、输入变化、冲突）记录 blocked，不循环消耗额度。超时需终止自己启动的进程树。

日志保存任务快照/摘要、版本、prompt、base/head、DSH JSONL/stderr、selftest与独立测试、审查、失败原因、时间和重试数。导出只发布去敏数据，不含机器个人路径或令牌。尚未实现的自动共享日志应明确 blocked，不能只实现 export 空壳后声称完成。

## 修正记录（第 2 轮自动修正）

按 Codex 的独立复现修复了 4 处真实集成失败，未改变已批准的范围与安全边界，也未修改 `game.js` / `test.cjs`：

1. `runcmd.spawnProcess` 已经负责写入并关闭 stdin，`dsh.drive` 随后又调用一次 `writeStdin`，真实 CLI 因此只看到空任务并报 `a task is required`。现在 prompt 只通过 spawn 契约传入一次。新增回归：真实 Node 假 CLI 子进程读取 stdin 到 EOF、输出安装版 JSONL 终止形状，断言收到非空 prompt 并返回 completed，且覆盖 `--session-id` 续跑 argv。
2. `doctor` 对 Electron ASAR 内的 `cliEntry` 使用 `fs.existsSync`，而该路径在 ASAR 内是虚拟的，导致把已由 `--version` 探测证明可用的条目误报为缺失。现在以 `<executable> --expose-internals <entry> --version` 探测为准（成功 = ok，失败 = failed，无法探测 = unverified），普通缺失路径仍然 failed。
3. `review.schema.json` 不满足 Codex strict Structured Outputs：嵌套对象（`acceptanceResults.items`、`findings.items`、`testEvidence.items`）的 `required` 未覆盖全部属性，API 在推理前返回 400。现在每个对象在任意深度都 `additionalProperties:false` 且把全部属性列入 `required`，缺省细节用 `""` / `0` 占位；控制器 validator 与固定提示同步更新，并新增递归 schema 回归。
4. PR 工作流顺序：在自测与范围/HEAD 校验之后、独立验收之前，按精确 head 推送业务分支并创建/复用同一个 Draft PR；验收失败保持 Draft 打开并写入具体反馈，通过后保持打开、不合并。新增顺序与幂等断言。
